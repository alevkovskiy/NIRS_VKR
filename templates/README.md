# Интерфейс NIRS

Страницы — обычный HTML без Jinja. Общие стили: `static/css/style.css`.
Поведение страниц: `static/js/app.js`. Все адреса API: `static/js/api.js`.
Внешние шрифты, библиотеки, сборщик и CDN не требуются.

`main.py` подключает `/static` и отдаёт HTML через `FileResponse`.
Пути вычисляются относительно файла приложения, а не текущей рабочей директории.
Запуск из корня репозитория в окружении с FastAPI и Uvicorn:

```sh
python -m uvicorn main:app --reload
```

Не открывайте страницы через `file://`: нужны HTTP-сервер и маршруты FastAPI.
JSON-обработчики реализованы. Данные берутся из PostgreSQL, GitHub и Ollama;
для работы нужен вход. При отсутствии GitHub каталог пайплайнов пуст.
FastAPI/Uvicorn объявлены в `pyproject.toml`, зависимости зафиксированы в `uv.lock`.
Настройка PostgreSQL, миграций и запуска через Docker описана в корневом README.

## Контракт JSON

Эта таблица описывает реализованный интерфейс. Актуальные модели запросов и
ответов также доступны в `/docs` и модуле `schemas/`.
Даты — строки ISO 8601 с часовым поясом, отсутствующие значения — `null`.
Все ID могут быть числами или строками. Все объекты списка имеют `id`.
Списки возвращаются массивом либо объектом `{"items": [...]}`.
Сервер должен возвращать списки чатов и запусков от новых к старым.

| Метод и URL | Тело / параметры | Ответ |
| --- | --- | --- |
| `POST /auth/send` | `{"email":"...","password":"..."}` | `{"access_token":"...","token_type":"bearer"}` |
| `POST /auth/register/send` | `{"email":"...","password":"..."}` | JSON либо `204`; затем интерфейс открывает вход |
| `GET /api/chats` | Необязательный поиск `?q=...` | Чаты: `id`, `title`, `created_at`, `last_activity_at` |
| `POST /chats/new` | `{}` | Созданный чат: `{"id":12}` |
| `GET /api/chats/{chat_id}` | — | `{"id":12,"title":"Вопрос","messages":[{"role":"user","content":"Привет"},{"role":"assistant","content":"Здравствуйте"}]}` |
| `POST /api/chats/{chat_id}/messages` | `{"content":"Текст вопроса"}` | `{"assistant_message":{"role":"assistant","content":"Ответ"}}` |
| `GET /api/pipelines` | — | Пайплайны: `id`, `name`, `description` |
| `GET /api/pipelines/{pipeline_id}` | — | Пайплайн: `id`, `name`, `description` |
| `POST /pipelines/{pipeline_id}/start` | `{}` или `{"branch":"main"}`; заголовок `Idempotency-Key` для защиты от повторов | Созданный запуск: `{"id":123}` |
| `GET /api/runs` | Необязательные `pipeline_id`, `result` | Запуски: `id`, `name`, `pipeline_id`, `pipeline_name`, `status`, `result`, `created_at` |
| `GET /api/runs/{run_id}` | — | Запуск со списком `jobs`, см. пример ниже |
| `GET /api/runs/{run_id}/status` | — | Полный актуальный запуск со списком `jobs`, тот же формат |
| `GET /api/jobs/{job_id}` | — | Джоба: `id`, `name`, `run_id`, `status`, `result`, `started_at`, `finished_at` |
| `GET /jobs/{job_id}/log` | — | Текст, `Content-Type: text/plain; charset=utf-8` |

Пример запуска:

```json
{
  "id": 123,
  "name": "Build #123",
  "pipeline_id": 7,
  "pipeline_name": "Aurora CI",
  "status": "completed",
  "result": "succeeded",
  "created_at": "2026-10-26T18:00:00Z",
  "started_at": "2026-10-26T18:00:05Z",
  "finished_at": "2026-10-26T18:03:00Z",
  "jobs": [
    {"id": "build-123", "name": "Build", "status": "completed", "result": "succeeded"}
  ]
}
```

`id` джобы должен однозначно определять её для `/jobs/{job_id}`. Если GitHub Actions
требует контекст запуска или попытки, сервер должен разрешать его сам либо
потребуется изменить маршруты и `api.js`.

Сообщения отправляются обычным запросом; потоковая генерация пока не используется.
Сервер сохраняет вопрос и ответ, чтобы после обновления они вернулись в `messages`.
После успешной отправки интерфейс добавляет оба сообщения в текущую переписку.
При сетевой ошибке текст сохраняется в поле: сначала проверьте историю, поскольку
сервер мог обработать запрос до обрыва соединения. Автоматических повторов POST нет.
Повторный запуск веб-клиентом защищён `Idempotency-Key`. При неопределённом
результате отправки нужно свериться с GitHub, а не создавать новый запрос вслепую. Опрос статуса идёт раз в 5 секунд и останавливается при завершении,
ошибке или уходе со страницы. Фоновая вкладка может опрашиваться реже браузером.

## Авторизация и ошибки

Токен сохраняется в `sessionStorage` текущей вкладки. Приватные запросы передают
`Authorization: Bearer <token>`. В URL токен не попадает. `401` удаляет токен
и предлагает вход. Кнопка выхода удаляет локальный токен и открывает вход.
Выход веб-клиента вызывает `POST /auth/logout` и отзывает текущую серверную сессию.
Если сервер недоступен, повторите выход после восстановления соединения.

HTML-оболочки общедоступны. Каждый приватный API-обработчик **обязан** проверять
токен и принадлежность чата/запуска/джобы пользователю. Скрытие элементов в браузере
не заменяет эту проверку. Токен доступен JavaScript; не вставляйте пользовательский
контент через `innerHTML`. Сейчас сообщения и логи выводятся через `textContent`.
Учётные данные GitHub Actions должны находиться только на сервере.

Для JSON-ошибок используйте, например, `{"detail":"Описание ошибки"}` с нужным
HTTP-статусом. Формат ошибок валидации FastAPI также поддерживается.
API не должен перенаправлять на страницу входа: возвращайте `401`.
Маршруты API используйте ровно с теми же завершающими `/`, что и в `api.js`:
перенаправления запросов намеренно запрещены, чтобы Bearer-токен не передавался
другому адресу.

## Дополнительные методы

- `POST /auth/logout` — отзыв текущего токена, ответ 204.
- `GET /api/system/status` — доступность модели и наличие настройки GitHub.
- `POST /api/runs/{id}/analysis` — новый чат с анализом завершённого прогона, ответ `{id}`.
- `GET /api/artifacts/{id}/download` — ZIP-архив артефакта, требует Bearer-токен.

Ответ прогона дополнен `branch`, `commit_sha`, `submission_error`, `artifacts`.
Статусы: `pending`, `queued`, `in_progress`, `completed`, `submission_failed`,
`submission_unknown`. Результат `partially_succeeded` передаётся в snake_case.
Регистрация и вход принимают пароль длиной от 8 до 128 символов.

# NIRS — сборки мобильного клиента и ИИ-анализ результатов

Веб-портал FastAPI + PostgreSQL для запуска пайплайнов GitHub Actions,
просмотра результатов и разбора журналов с локальной Qwen3.5 9B через Ollama.
Предметная область — сборка и проверка Qt/QML-клиента ОС Аврора.
Другие мобильные платформы подключаются собственными пайплайнами и агентами.

## Запуск на этом Mac

1. Откройте Docker Desktop и Ollama. Модель `qwen3.5:9b` уже скачана.
2. Из корня проекта:

```sh
docker compose up -d --build --wait
```

3. Откройте http://localhost:8000/auth/register, создайте аккаунт и войдите.
4. Откройте «ИИ-ассистент», создайте чат и отправьте сообщение.

Сайт: http://localhost:8000. Документация API: http://localhost:8000/docs.
Состояние базы и схемы: http://localhost:8000/health/ready.
На главной странице после входа показываются доступность модели и настройка GitHub.
Для чата GitHub не требуется. Если GitHub не настроен, список пайплайнов пуст;
фиктивные сборки и результаты не создаются.

```sh
docker compose logs --tail=50 app
docker compose stop
docker compose up -d --wait
```

Остановленные контейнеры сохраняют данные в Docker volume `postgres_data`.
Команда `docker compose down -v` удаляет это хранилище — не используйте её,
если данные нужны.

## Что реализовано

- Регистрация, вход, хеширование паролей scrypt, ограничение попыток входа.
- Серверные сессии: в базе хранится хеш токена, срок по умолчанию 24 часа.
- Выход в веб-интерфейсе отзывает текущую сессию на сервере.
- Личные чаты, поиск, история и ответы Ollama с контекстом предыдущих сообщений.
- Сохранение вопроса и ответа одной транзакцией; при сбое модели история не меняется.
- Защита от одновременной генерации в одном чате, ограничение одного запроса к модели
  на процесс сервера для компьютера с 16 ГБ памяти.
- Список настроенных пайплайнов, выбор ветки, запуск GitHub и локальная история.
- Проверка владельца чата, прогона, задачи, журнала и скачиваемого артефакта.
- Опрос GitHub, сопоставление статусов, задачи, журналы и ZIP-архивы артефактов.
- Анализ завершённого прогона в отдельном чате с данными запуска и фрагментами логов.
- Защита веб-запуска от повторов через `Idempotency-Key`.
- Миграции Alembic, Docker, тесты на PostgreSQL, CI портала и pipeline клиента Авроры.

Реальный запрос к Ollama проверен локально. GitHub-интеграция проверена тестами
с подменой HTTP-ответов и ответов сервиса. Реальная сборка RPM ещё не проверена:
пока не установлен и не зарегистрирован Linux x86_64-исполнитель с Aurora SDK.
Офлайн-установщик 5.1.2.10 скачан в `sdk/` и проверен по контрольной сумме;
скачанный файл ещё не означает установленный SDK.

## Настройки

`.env` уже создан локально со случайным паролем PostgreSQL и исключён из Git.
Для новой машины скопируйте `.env.example` в `.env` и замените пароль в обеих
строках `POSTGRES_PASSWORD` и `DATABASE_URL`.

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | PostgreSQL для Python, запущенного на ноутбуке |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Инициализация базы Docker |
| `POSTGRES_PORT` | Локальный порт базы, по умолчанию 55432 |
| `APP_PORT` | Локальный порт сайта, по умолчанию 8000 |
| `OLLAMA_URL` | Адрес Ollama для Python на ноутбуке |
| `DOCKER_OLLAMA_URL` | Адрес Ollama из контейнера: `http://host.docker.internal:11434` |
| `OLLAMA_MODEL` | `qwen3.5:9b` |
| `OLLAMA_TIMEOUT` | Ожидание ответа, по умолчанию 90 секунд |
| `GH_OWNER`, `GH_REPO`, `GH_ACTIONS_TOKEN` | Доступ к GitHub, пока пустые |

При смене порта PostgreSQL измените и `DATABASE_URL`. Для Compose используйте
локальный пароль из букв и цифр: специальные символы в URL требуют кодирования.
Изменение пароля в `.env` не меняет пароль в уже инициализированном volume.
После изменения настроек контейнер пересоздаётся через `docker compose up -d`.

## Разработка без контейнера приложения

Нужны Python 3.14 и uv. PostgreSQL остаётся в Docker:

```sh
docker compose up -d --wait db
docker compose stop app
uv sync --locked
uv run alembic upgrade head
uv run uvicorn main:app --reload
```

Структура и транзакции: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Подключение реальных сборок

Пошаговая инструкция: [docs/GITHUB_SETUP.md](docs/GITHUB_SETUP.md).
После создания пайплайна задайте GitHub-переменные в `.env`, пересоздайте контейнер
и добавьте его реальный ID:

```sh
docker compose exec app python manage.py add-pipeline --workflow aurora.yml --name "Клиент Авроры"
```

Файл `aurora.yml` должен быть опубликован в `.github/workflows/` основной ветки
репозитория. Повторная команда обновляет запись. Для проверки самого портала
добавьте отдельный процесс с `--workflow portal.yml --name "Проверка портала"`.
Далее выберите его на сайте, укажите ветку и запустите сборку.
Артефакт скачивается ZIP-архивом, внутри которого будет RPM или отчёт.

## Миграции

```sh
uv run alembic revision --autogenerate -m "describe change"
# Сначала просмотрите сгенерированный файл.
uv run alembic upgrade head
uv run alembic check
```

Структура меняется миграциями, а не `create_all()` при каждом старте.
Откат миграций выполняйте только в тестовой базе: он может удалить данные.

## Проверки

```sh
uv run ruff check config.py database.py security.py manage.py models schemas main.py routers services crud migrations tests
uv run pytest -q
node aurora_client/tests/contract.test.cjs
```

Без `TEST_DATABASE_URL` проверки базы пропускаются. Для полного локального прогона
уже создана отдельная база `nirs_test` на порту 55432. Задайте `DATABASE_URL` и
`TEST_DATABASE_URL` с теми же реквизитами, что в `.env`, но базой `nirs_test`;
примените миграции и выполните `pytest`.
Не указывайте рабочую базу в `TEST_DATABASE_URL`. Записи тестов откатываются.
В CI тестовая PostgreSQL создаётся автоматически и отдельно от базы разработки.
Проверенные сценарии и ограничения: [docs/VALIDATION.md](docs/VALIDATION.md).

## CI/CD

- `.github/workflows/portal.yml` — CI портала: миграции, тесты, контракт клиента,
  сборка Docker-образа и публикация небольшого отчёта тестов.
- `.github/workflows/aurora.yml` — отдельная сборка и валидация RPM на агенте с SDK.
- `scripts/build-aurora.sh` — команда сборки для установленного Aurora SDK.
- `.github/workflows/deploy.yml`, `compose.production.yaml`, `scripts/deploy.sh` —
  шаблон ручной доставки на подготовленный сервер с резервной копией базы.

Внешние процессы активируются после публикации `.github/workflows/` в GitHub.
Для запуска кнопкой сайта нужен отдельный токен `GH_ACTIONS_TOKEN`; подключение
GitHub к помощнику не передаёт этот токен веб-приложению.
Доставка на постоянный сервер пока не включена: сервер и домен не определены.
Локальная сдача диплома работает через Docker Compose. Перед публичным размещением
нужно настроить HTTPS, ограничение регистрации, резервное копирование и политику
доступа к сборкам. Текущий Compose публикует порты только на localhost.

## Клиент Авроры

Исходники: `aurora_client/`. Адрес сервера меняется в настройках клиента.
Виртуальная машина или устройство не увидят Mac по своему `localhost`.
Для подключения устройства потребуется доступный ему адрес и отдельная настройка
прослушивания сервера; наружу PostgreSQL и Ollama публиковать не требуется.
Сборку, установку и C++-проверки нужно выполнить в SDK, см. `aurora_client/README.md`.
